Kubernetes 1.33 因 Go 1.24 預設啟用後量子金鑰交換，但版本不一致會悄悄降級

Kubernetes 官方部落格刊出 ControlPlane 工程師 Fabian Kammel 的文章：Kubernetes v1.33 使用 Go 1.24，因此其 TLS 連線預設就支援 X25519MLKEM768 混合後量子金鑰交換，但 Go 版本不一致時會無聲降回傳統加密。

這是什麼

TLS 連線有兩個要保護的環節：金鑰交換（雙方約定加密用的共享祕密）與數位簽章（驗證對方身分）。文章主張前者對『先收集、日後解密』攻擊最急迫，所以先導入的是混合金鑰交換；簽章與憑證的後量子遷移則仍落後。

三點帶走

  1. Kubernetes v1.33 因採用 Go 1.24，預設支援 X25519MLKEM768 混合後量子金鑰交換。
  2. Go 1.23 與 1.24 的後量子群組不同，版本不一致時連線會悄悄降回傳統加密。
  3. 後量子簽章與憑證遷移仍在早期，金鑰與簽章較大、工具鏈支援不足。

重點與分析

文章表示，Go 1.24 的 crypto/tls 預設啟用 X25519MLKEM768；Kubernetes v1.33 使用 Go 1.24，且未明確設定 Config.CurvePreferences。

因此作者推論 v1.33 不需要專屬公告或 KEP（Kubernetes 增強提案）就具備混合後量子金鑰交換。文中用 Minikube 實測：以 OpenSSL 3.5.0 連 API server，輸出『Negotiated TLS1.3 group: X25519MLKEM768』。這是作者個人的實測示範，並非 Kubernetes 專案的正式功能聲明。

文章表示，Kubernetes v1.32 用 Go 1.23 的草案群組；v1.33 的 kubectl 連 v1.32 API server 時，雙方無共同後量子演算法，會悄悄降回傳統加密。

這是全文最實用的警告：使用者可能以為已受後量子保護，升級用戶端後反而失去保護，而且沒有錯誤訊息。文章據此強調要理解 Go 版本升級對 TLS 堆疊的影響。這個風險是邏輯推導出的情境，不是文中回報的實際事故。

文章表示，ML-KEM-768 公鑰約 1.2 KB，可能使 TLS ClientHello 放不進單一 TCP 封包（常見上限 1500 位元組）。

這個問題與演算法安全無關，而是封包大小對舊假設的衝擊：有些函式庫或設備假設 ClientHello 一定在單一封包內。文章表示這在部分 Kubernetes 相關專案與網路元件中已被觀察到，可能造成連線失敗，並指向 tldr.fail 取得更多細節。

文章表示，Dilithium2 金鑰可比 Ed25519 大 30 倍、憑證大 12 倍，效能差 10 到 1000 倍；Go 的 ML-DSA 最快可能在 Go 1.26 出現。

文章還提到根憑證有效期長、安裝在許多裝置與作業系統中，升級困難，是簽章遷移的另一個障礙；NIST 另在進行第二輪簽章標準化。Cloudflare（NET） 的 CIRCL 與 cfgo 可實驗 Ed25519-Dilithium2 憑證，但需要自訂 Go 工具鏈，不屬於主流 Kubernetes 或 Go 發行版。

文章引用 NIST 報告：使用傳統密碼的系統應在 2030 年後棄用、2035 年後禁止。

這個時間表是作者用來說明『現在就要開始遷移』的依據，文章同時承認很難預測量子電腦何時能破解傳統演算法。支援進度方面，文中列出 Chrome 131（2024 年 11 月）、Firefox 135（2025 年 2 月）、OpenSSL 3.5.0（2025 年 4 月）已支援混合方案，Apple（AAPL） 預計在 26 版作業系統推出。
