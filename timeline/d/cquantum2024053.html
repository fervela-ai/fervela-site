Chrome 桌面版預設啟用後量子 Kyber，並談憑證敏捷性

Chromium 團隊說明，此舉可防堵「先儲存、後解密」攻擊，同時指出後量子簽章太大，網路 PKI 需要先具備信任錨敏捷性。

這是什麼

現行網路加密中，金鑰交換與數位簽章用的公開金鑰演算法都怕量子電腦。Chrome 把 Kyber（後來被 NIST 標準化為 ML-KEM）與傳統 X25519 組成混合式金鑰交換，即使其中一種被破解仍有另一種保護。這篇文章說明已上線的部分與尚未解決的部分。

三點帶走

  1. 官方宣布 Chrome 124 起桌面版預設啟用 Kyber 混合金鑰交換，Android 暫未推出。
  2. 官方稱 Kyber 使 TLS 交握中位延遲增加 4%，ML-DSA 簽章約為 ECDSA 的 40 倍。
  3. 官方提議以多憑證部署達成信任錨敏捷性，屬提案階段。

重點與分析

官方宣布，自 Chrome 124 起，已在所有桌面 Chrome 平台為 TLS 1.3 與 QUIC 預設啟用最新的 Kyber 草案規格。

這是實際上線的變更，而不是路線圖。官方說明這是『機會性』的量子抗性金鑰交換：伺服器若支援，就能在連線中使用。上線過程揭露了數個既有 TLS 中間盒產品的錯誤，Chrome 因此提供暫時性的企業政策可關閉此功能。這顯示後量子遷移的現實阻力常來自舊設備，而非演算法本身。

官方說明，『先儲存、後解密』攻擊是今日最急迫的量子威脅，防禦要靠量子抗性的金鑰交換。

攻擊者可先記錄加密流量，等到密碼學相關量子電腦出現再解密，所以保護機密期很長的資料要及早換金鑰交換。官方比較認證（簽章）的威脅：偽冒攻擊只在量子電腦實際存在後才有效，因此遷移認證的急迫性較低。這個區分決定了 Chrome 先做金鑰交換的順序。

官方表示，Kyber 每方傳送約 1KB，而 X25519 只有 32 位元組，增加超過 30 倍，使桌面版 TLS 交握中位延遲增加 4%。

封包變大使 ClientHello 被拆成兩個封包。官方說在桌面平台因連線重用，影響不到 Core Web Vitals 的可感範圍，但在頻寬較低、延遲較高的 Android 上會被感受到，所以尚未在 Android 推出。這是少見的公開量化代價，說明後量子密碼的成本主要是資料量而非計算速度。

官方表示，ML-DSA（Dilithium）的金鑰與簽章約為 ECDSA 的 40 倍，直接替換會讓 TLS 交握增加約 14KB；Cloudflare（NET） 預期延遲將增加 20% 至 40%。

典型 TLS 連線用兩把公鑰與五個簽章，所以簽章變大的影響被放大。官方因此主張要找到傳輸更少簽章與公鑰的替代認證方法，而不是單純換演算法。20% 至 40% 是 Cloudflare（NET） 的預期值，並非實測，屬於推估。

官方提出，應轉向多憑證部署模型，讓伺服器依客戶端自動送出對應憑證，以實現信任錨敏捷性，使新舊客戶端能以不同速度演進。

目前一個網站通常只配一張憑證，必須同時被所有支援的瀏覽器信任，導致網路 PKI 很難演進。多憑證模型能讓較新的客戶端使用後量子信任錨，不必等最慢的一方。這是官方提出的方向，文中沒有標示何時實作，因此仍屬提案階段。

通鑑怎麼看

通鑑認為，這篇文章最有價值的是公開了後量子遷移的實際成本與阻力：金鑰交換已能上線，簽章與憑證體系則被大小與相容性卡住。官方稱的延遲數字是自家量測，Android 的實際影響尚未公布。
