Chiplet Cloud：以小晶片 ASIC 打造大型語言模型推論超級電腦（論文）｜研究團隊（arXiv）｜7 月 5 日 事件進階

用數千顆小晶片把模型全塞進 SRAM：Chiplet Cloud 挑戰 GPU 推論成本

這篇 7 月 5 日首次提交到 arXiv 的論文，從「每個 token 花多少錢」出發，設計一套專門服務生成式語言模型的晶片與伺服器架構。

這是什麼

ASIC（特定應用積體電路）是只為某一類工作設計的晶片。Chiplet Cloud 的構想是用大量重複的小晶片加速器，把模型參數全部放進晶片內的 SRAM（靜態隨機存取記憶體，速度快但密度低），避開外部 HBM 或 DDR 的頻寬瓶頸。

三點帶走

  1. Chiplet Cloud 以大量小晶片 ASIC 把模型參數全放進晶片內 SRAM。
  2. 作者宣稱每 token TCO 比租用 GPU、TPU 雲端改善 97 倍與 18 倍。
  3. 結果來自模擬與建模，沒有實際製造晶片。

重點與分析

論文表示，Google（GOOGL） 搜尋估計每秒處理超過 99,000 次查詢，而 GPT-3 在 GPU 上的最佳吞吐量是每張 A100 每秒 18 個 token；若每次查詢都嵌入 GPT-3 並產生 500 個 token，需要 340,750 台 DGX 伺服器（272.6 萬張 A100）。

作者用這個思想實驗說明「拿通用 GPU 服務大型語言模型撞到擴充牆」。數字引用自其他文獻，屬於推算而非實測，且假設每次查詢都要產生 500 個 token，條件相當極端。但它點出論文的核心問題意識：訓練是一次性成本，推論是每天持續的成本，推論硬體的經濟性決定了大模型能否普及。

論文表示，Chiplet Cloud 讓所有模型參數與 KV 值存放在名為 CC-MEM 的可擴充晶片內記憶體系統，並用經過調校、可大量複製的小晶片加速器模組降低製造成本；CC-MEM 內含壓縮解碼單元，以「壓縮儲存、展開讀取」機制支援稀疏模型。

這是架構的關鍵賭注：用昂貴但頻寬極高的 SRAM 取代 HBM。論文自己也承認 SRAM 每位元較貴，必須仔細權衡晶片面積、記憶體容量與頻寬、晶片數量，才能讓製造成本與效能平衡。壓縮機制則讓同樣的 SRAM 能放下更大的稀疏模型，作者宣稱 60% 稀疏度時可支援 1.7 倍大的模型。

論文表示，團隊採用兩階段軟硬體協同設計方法：硬體探索階段由下而上搜尋從加速器到 1U 機架伺服器的設計空間，考量功耗、平面配置與散熱限制；軟體評估階段再針對特定工作負載分析效能與 TCO，並搜尋配套的軟體映射策略。

一般做法是硬體先定、再找最佳軟體映射；論文把順序反過來，在所有可能的硬體組合上同時搜尋映射策略。這種方法論的價值在於把成本模型放進設計迴圈。不過這仍是模擬與建模結果，論文沒有實際製造出 Chiplet Cloud 晶片，所有數字都來自模擬器。

論文表示，在八個熱門大型語言模型上，調校後的 Chiplet Cloud 伺服器每 token TCO 比租用 GPU 與 TPU 雲端改善 97 倍與 18 倍，比自建 GPU 與 TPU 雲端改善 8.3 倍與 3.7 倍。

「租用」與「自建」兩組數字差距很大，說明雲端租金本身包含大量利潤與營運成本。比較對象是當時的 GPU 與 TPU 世代，且 Chiplet Cloud 只做推論、只針對特定模型調校，屬於專用與通用的不對等比較。本頁抓取的是 2024 年 5 月的第四版，摘要已提到後來的 Gemini 模型，日期以首次提交的 2023 年 7 月 5 日為準。

通鑑怎麼看

通鑑認為，這篇論文代表 2023 年中學界對「推論成本」的系統性回應：與其等通用 GPU 降價，不如為大型語言模型設計專用小晶片。數字來自模擬，但「全部塞進 SRAM」的思路在後續多家推論晶片新創身上都看得到。
