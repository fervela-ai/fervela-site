Google 讓 AI 代理按需翻工具說明書

Google 在 Gemini API 推出測試版 Tool Retrieval，讓 AI 代理需要使用工具時，才載入完整的操作細節。

這是什麼

AI 代理要替人辦事，得知道各種工具能做什麼、該填哪些資料。Tool Retrieval 像先看工具目錄，選定工具後才翻開詳細說明書，讓大型工具庫不必每次都塞進請求。

三點帶走

  1. AI 代理先看工具目錄，需要時才讀完整填寫規則。
  2. 搜尋、載入與呼叫的步驟可在同一次請求中檢查。
  3. 省下的詞元要扣除搜尋與實際載入工具的成本，應用自己的流量衡量。

重點與分析

官方表示，延後載入的工具仍會顯示名稱與用途說明；完整的參數結構只在當前任務需要時，才由 API 載入。

通鑑判斷，這解開的是工具越接越多、每次提問卻都得附上整本操作手冊的卡關。參數結構就是工具要求填寫的欄位與格式，例如退款要有訂單編號和金額。以前即使只查一筆訂單，AI 代理也可能收到所有工具的填寫規則；現在它先看目錄，再讀選中工具的規則。工具多的團隊因此有機會減少重複傳送的內容，也讓 AI 先從較短的清單判斷該用哪個工具。

官方示例中，AI 代理為受損訂單尋找退款工具、載入所需參數，再提出退款呼叫；這些步驟都記錄在同一次 API 請求中。

通鑑認為，同一次請求內完成搜尋、載入與呼叫，改變的是開發者排查錯誤的方式。若 AI 選錯工具，開發者可以沿著步驟查看它搜尋了什麼、取得了哪份工具說明，再判斷問題出在名稱、用途描述或後續填入的資料。這比只看最後呼叫結果更容易找到癥結。示例最後仍由應用程式執行退款並回傳結果；對使用者來說，關鍵是代理能更順地找到辦事入口，實際動作仍接在原本的工具流程上。

官方表示，常用工具可預先載入，其餘按需載入；遠端 MCP 伺服器提供的工具也能使用這套方式，無須逐一列出。

通鑑判斷，這條路適合工具種類很多、但每件事通常只動用少數工具的服務。像辦公室有一整排抽屜，常拿的文具放桌上，少用的留在抽屜裡；每次工作只取眼前需要的東西。官方也說，延後載入的規則不會擠進請求開頭，有利於讓可重複使用的開頭內容保持一致。對串接大型工具庫的團隊，價值不只是少傳資料，也包括保留常用工具的直接入口，不必把所有工具一律改成先搜尋。

官方表示，此功能沒有另收費用，但搜尋工具會增加一小塊固定的輸入詞元；載入後的工具規則也按標準費率計費。

通鑑認為，是否省錢要看實際使用情況，不能只看功能名稱。詞元可以理解成計費時切分的文字單位：少送進去的工具說明會減少輸入量，搜尋步驟和實際載入的說明則會把一部分加回來。官方的判斷條件是：從未載入的工具規則合計多於實際載入的規則時，才會節省詞元。若團隊需要自行管理工具目錄或依使用者權限篩選，也能改由自己的程式搜尋，但每次搜尋會多一趟往返。

通鑑怎麼看

通鑑認為，Tool Retrieval 的重點是讓 AI 代理接得起更大的工具庫，同時保有清楚的選用過程。它把工具名稱與詳細填寫規則分開處理；成效最值得看的是實際流量中少送了多少詞元，以及代理選錯工具的情況是否減少。
