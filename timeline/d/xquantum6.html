Cloudflare Workers 加入 ML-KEM 與 ML-DSA 支援｜Cloudflare｜10 月 1 日 事件推薦

Cloudflare（NET） 把後量子密碼工具放進 Workers，讓開發者能開始改造應用

Cloudflare（NET） 在官方文章中介紹 Workers 新增的後量子密碼功能，以及開發者可以如何試用。

這是什麼

Cloudflare（NET） Workers 的 Web Crypto 新增金鑰封裝與數位簽章功能。開發者可用它們測試應用如何改用後量子演算法，但仍須自行把這些工具接進完整的通訊流程。

三點帶走

  1. Workers 新增後量子金鑰封裝與簽章工具，開發者須啟用相容性旗標。
  2. 金鑰封裝負責建立共同秘密；完整加密仍須由通訊流程接續完成。
  3. 評估採用時，要同時檢查函式庫整合，以及金鑰與簽章變大後的成本。

重點與分析

官方表示，Workers 現在提供 ML-KEM 金鑰封裝與 ML-DSA 簽章功能；開發者可直接透過 Web Crypto 呼叫，不必另行打包密碼演算法程式。

可以把 Web Crypto 想成程式環境附的工具箱：以前缺少後量子工具，開發者想試，就得自己挑選、帶入並維護另一套工具。通鑑判斷，這次解開的是試作時的第一道卡關。當底層功能由 Workers 提供，使用同一環境的函式庫便有機會共用它；開發者可以把力氣放在檢查既有程式如何接上新演算法，而非每個團隊都先處理工具的安裝與維護。

官方說明，ML-KEM 讓通訊雙方取得相同的秘密金鑰材料；範例中的金鑰封裝步驟本身尚未加密訊息。

這像雙方先約好一把鎖的鑰匙，還沒把信放進上鎖的盒子。真正要保護訊息，還得由其他通訊流程利用這份金鑰材料。通鑑認為，分清這兩步，才看得懂這項更新改變了哪個環節：Workers 補上了建立共同秘密所需的底層能力，讓依賴它的流程有機會選用後量子演算法。對正在規畫轉換的團隊，工作重點因此是檢查整條通訊流程如何銜接，而非只替換一個函式名稱。

官方以簽署及驗證 JWT 為例，展示函式庫如何呼叫 Workers 提供的 ML-DSA 簽章功能。

數位簽章可以想成附在電子文件上的防偽印記：接收者拿公開金鑰檢查，確認內容與簽章是否相符。JWT 是容易理解的例子，因為範例分別展示簽署與驗證。通鑑判斷，這條路的關鍵是讓既有函式庫把簽章工作交給執行環境。若函式庫能順利銜接，應用程式處理 JWT 的方式就能沿用熟悉的結構，減少每個應用各自攜帶密碼演算法程式的負擔。

官方指出，HPKE 可利用 ML-KEM 提供的金鑰材料建立完整加密流程；相關函式庫可在 Workers 提供該功能時選用它。

從取得共同秘密到傳送加密訊息，中間還有組合演算法的工作。HPKE 是把這些步驟接起來的一種流程；官方也提到使用 HPKE 的 OHTTP。通鑑認為，這顯示 Cloudflare（NET） 選的是由底層往上支援現有通訊流程的路，而非替每種用途各做一套新功能。接下來最具體的觀察點，是相關函式庫能否完成所需的 Workers 整合，讓開發者在實際流程中選用這些功能。

官方表示，功能目前須啟用相容性旗標；ML-DSA 的公開金鑰與簽章也比 RSA 或 Ed25519 大得多。

相容性旗標像一道由開發者自行打開的開關，適合先檢查現有程式能否接上新功能。通鑑判斷，接下來的取捨會出現在資料傳送與儲存：Workers 內建演算法可減少應用程式打包額外程式碼，卻不會縮小傳出去的簽章，或存起來的金鑰。團隊評估時應同時看整合是否順利，以及採用新簽章後，憑證大小、傳輸量和儲存需求如何變化；只看程式碼是否變少，會漏掉另一半成本。

通鑑怎麼看

通鑑認為，這次更新的價值在於把後量子轉換變成開發者能動手檢查的工作：先用 Workers 的底層工具接入既有函式庫，再逐段檢查簽章與加密流程。它能降低試作門檻；真正影響採用速度的，將是函式庫整合與較大金鑰、簽章帶來的成本。
