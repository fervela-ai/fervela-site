AWS Private CA 支援 ML-DSA 後量子簽章與程式碼簽署｜Amazon Web Services｜11 月 17 日 事件推薦

AWS 以 Private CA 與 KMS 示範 ML-DSA 後量子程式碼簽署

繼 KMS 支援 ML-DSA 之後，AWS Private CA 也能簽發 ML-DSA 憑證，部落格以程式碼簽署為例示範整條流程。

這是什麼

ML-DSA 是 NIST 標準化的後量子數位簽章演算法（FIPS 204），用來證明軟體或身分沒有被偽造。私有 CA 是企業自建的憑證簽發單位；這次讓企業的整條憑證鏈和簽章都能改用後量子演算法。

三點帶走

  1. AWS Private CA 新增 ML-DSA 支援，搭配 KMS 的 ML-DSA 金鑰可做後量子程式碼簽署。
  2. 範例用 ML-DSA-65，簽章為 CMS 分離式，OpenSSL 3.5 以上即可驗證。
  3. 驗證者需預先配置後量子根；範例信任庫不能直接用於正式環境。

重點與分析

官方表示，AWS Private CA 現已支援 ML-DSA 後量子簽章，客戶可建立自行管理的量子抗性信任根，用於程式碼簽署與裝置驗證等。

信任根壽命很長，是後量子遷移的優先項目：官方在文中說，系統若需要長時間維持安全，就必須儘早建立量子抗性的根。公告列出的用途包括程式碼簽署、裝置驗證、搭配 IAM Roles Anywhere 的 AWS 外部工作負載驗證，以及使用私有 PKI 的 mTLS 與 IKEv2/IPsec 通道。注意是「私有」PKI，也就是企業自己掌握驗證者的範圍，並不等於公開網站憑證。

官方表示，範例使用 ML-DSA-65 變體，建立根 CA、下級 CA 與程式碼簽署憑證，整條憑證鏈都是量子抗性的 ML-DSA 憑證。

金鑰對在 AWS KMS 內產生，簽署時私鑰留在 KMS 裡，公鑰則放進由下級 CA 簽發的憑證，分工清楚。範例程式為 diy-code-signing-kms-private-ca，用 AWS SDK for Java 實作，並可用 OpenSSL 3.5 以上版本檢視憑證與驗證簽章。這表示要驗證後量子簽章，工具鏈也需要先升級。

官方表示，簽章採 CMS 分離式簽章，摘要演算法為 SHAKE256，ML-DSA 在 CMS 的用法由 RFC 9882 規範。

分離式簽章不含原始資料，可搭配原檔以 OpenSSL 等標準工具驗證。文章特別指出，驗證不需要 AWS 憑證，也不必呼叫 KMS 的驗證 API，只要驗證者預先載入根憑證即可。這讓簽署端在雲端、驗證端在裝置或其他環境的架構成為可能。

官方表示，範例只用一個 ML-DSA 簽章，但有些情境可採傳統加後量子的雙簽章，以便與只支援傳統簽章的舊驗證者相容。

文章同時點出兩個限制。其一，驗證者必須預先配置後量子 PKI 根，才能保證軟體無法被擁有 CRQC（足以破解密碼的量子電腦）的對手偽造。其二，示範程式的信任庫只是 Java 物件，並非作業系統或瀏覽器的信任庫，若要用於正式環境必須改成主機端的信任庫。這提醒讀者，範例是教學用途，上線前還要補強。

通鑑怎麼看

通鑑認為，這則的實質意義是後量子遷移從金鑰（KMS）延伸到憑證與簽署流程；對需要長期維持可信度的裝置與軟體簽署，是可以先行試驗的工具，但驗證端的工具與信任根佈署仍要自己處理。
