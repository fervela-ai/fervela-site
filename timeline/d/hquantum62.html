AWS 發布 Python 應用測試後量子 TLS 的方法｜Amazon Web Services｜7 月 24 日 事件延伸

AWS 示範在 Python 測試後量子混合 TLS，並提供 OpenSSL 3.5 容器範例

AWS 安全部落格說明如何在 Python 應用程式中測試後量子（PQ）混合 TLS：AWS 伺服器端已在推出混合 TLS，客戶端則需要 OpenSSL 3.5，因此 AWS 提供一份內含 OpenSSL 3.5 的容器定義，方便測試。

這是什麼

TLS 是網站與 API 連線加密的協定。混合 TLS 在傳統金鑰交換之外加上 ML-KEM（後量子金鑰封裝演算法），目的是讓今天被錄下的加密流量，未來更難被量子電腦解開。這篇是操作教學，教開發者在自己的網路環境驗證能否順利協商這種連線。

三點帶走

  1. AWS 伺服器端正透明推出 ML-KEM 混合 TLS，客戶端需要 OpenSSL 3.5 才能協商。
  2. AWS 提供含 OpenSSL 3.5 的容器範例，可測 ssl socket、requests、boto3 與 AWS CLI。
  3. ML-KEM 金鑰較大，需確認自己網路中的設備能處理較大的握手封包。

重點與分析

官方表示，AWS 目前以混合設定部署 PQ TLS，傳統金鑰交換與 ML-KEM 並用以深度防禦；AWS 正在伺服器端透明地推出，客戶不需任何設定。

伺服器端由 AWS 負責，客戶需要處理的是客戶端軟體。要成功協商混合 TLS，連線兩端都必須支援。因此這篇文章要解決的是客戶端：如何讓 Python 程式具備這個能力。

官方表示，Boto3 依賴 Python 的 ssl 模組，通常使用作業系統的 OpenSSL；OpenSSL 3.5 預設啟用混合 TLS，但大多數作業系統發行版還沒有以它為預設。

這是這份教學存在的理由：多數開發者在預設環境裡不會有 OpenSSL 3.5。AWS 的解法是提供容器定義，在標準 Python 外加裝 OpenSSL 3.5，並附 boto3 與 requests 等套件，也提供 AWS CLI、requests、標準函式庫 ssl 三種連線的範例。

官方表示，ML-KEM 的金鑰比傳統方案大很多，因此混合 TLS 握手要傳送與接收更多資料，需在自己的網路中驗證資安設備與網路設備能否正確處理。

這是實務上最需要注意的一點：問題不在演算法安全，而在中間設備是否能處理較大的握手封包。文章沒有給出具體的位元組數字，只建議用範例實際測試自己的網路路徑；若要測試自己機器到 AWS 的網路路徑，必須在本機而不是雲端環境建置並執行容器。

官方表示，測試成功時會顯示 OpenSSL 3.5.0 並對 ssl socket、requests、boto3 與 AWS CLI 皆輸出 ok；封包擷取中可看到 X25519MLKEM768 被選入伺服器 Hello 訊息。

驗證方式是抓封包，在 TLS 握手的 key_share 擴充中尋找該混合群組。X25519MLKEM768 是把 X25519 傳統金鑰交換和 ML-KEM-768 合併的群組名稱。範例使用 Secrets Manager 的 ListSecrets 做唯讀測試，不會回傳機密值。文章另外有一則更新註記：2025 年 7 月 29 日更正了確認協商章節的指令描述。
