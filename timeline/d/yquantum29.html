AWS Secrets Manager 用戶端支援混合式後量子 TLS｜AWS｜4 月 14 日 事件延伸

AWS 把後量子保護帶到擷取機密資料的連線

AWS 宣布，Secrets Manager 用戶端支援混合式後量子 TLS，讓應用程式擷取機密資料時可使用結合傳統與後量子密碼技術的連線。

這是什麼

這次更新的是用戶端擷取資料時的連線：金鑰交換同時採用傳統機制與 ML-KEM，降低資料今天被留存、未來再遭破解的風險。

三點帶走

  1. 混合式 TLS 讓傳統機制與 ML-KEM 一起保護擷取機密資料時的連線。
  2. 指定用戶端版本已自動支援；使用 SDK 的程式需核對各自的版本條件，Java v2 另須參照文件。
  3. 更新後可查 CloudTrail 的 GetSecretValue 紀錄，確認連線選用的金鑰交換演算法。

重點與分析

AWS 表示，擷取機密資料的 TLS 連線可結合傳統金鑰交換與後量子密碼技術 ML-KEM。

可以把金鑰交換想成雙方先約好一把只有彼此能用的鎖，再傳送機密資料。這次更新的是擷取機密資料時 TLS 連線所用的金鑰交換。通鑑判斷，混合設計的關鍵，在於讓既有的傳統保護與面向未來量子風險的保護同時參與連線；企業無須等到量子電腦真的能破解現行機制，才開始處理今天傳送的資料可能被留存、日後解密的問題。

AWS 表示，指定版本的 Secrets Manager Agent、Lambda Extension 與 Secrets and Configuration Provider 已自動啟用這項支援。

對使用這三種工具擷取機密資料的團隊，變動落在用戶端版本。通鑑認為，這比要求每個應用程式各自改寫連線流程更容易納入既有維護工作：團隊先確認目前使用哪一種工具、版本是否符合條件，再檢查實際連線。AWS 舉出微服務啟動時需擷取多筆機密資料的例子；AWS 舉的例子正是更新 Agent 後，讓這段擷取過程使用具後量子保護的 TLS 連線。

AWS 表示，使用 SDK 擷取機密資料的程式，也可透過受支援的 Rust、Go、Node.js、Kotlin、Python 與 Java v2 SDK 使用混合式金鑰交換。

通鑑判斷，這項支援讓沒有採用上述 Agent 或擴充工具的應用程式也有升級路徑，但「使用某種程式語言」與「目前連線已採用新機制」是兩個不同的檢查項目。AWS 對 Python 列有 OpenSSL 版本條件，對 Java v2 也列出版本門檻及額外處理說明；實務上應依程式所用的工具包與相依版本逐項確認。

AWS 表示，已升級至最新用戶端版本的使用情境，除 Java v2 須參照文件處理外，無須修改程式碼或設定，也無須另做遷移。

後量子密碼轉換最容易卡在「誰要改、要改多少」。通鑑認為，AWS 這次把主要工作收斂為用戶端升級，有助於讓團隊沿用既有的更新流程；但 Java v2 被單獨列為例外，不能把「升級即可」套用到所有應用程式。對負責維護的人來說，較有用的工作清單是盤點擷取機密資料的方式、確認相應版本，再依 AWS 文件處理 Java v2。

AWS 表示，可在 CloudTrail 的 GetSecretValue 呼叫紀錄中，檢查 tlsDetails 欄位是否記載 X25519MLKEM768，以確認混合式金鑰交換已啟用。

功能支援寫在公告裡，與自己的連線實際選用該功能，是兩件事。CloudTrail 提供了可查的紀錄，讓團隊能從一次擷取機密資料的呼叫，核對所用的金鑰交換演算法。通鑑判斷，這是整次更新最實用的驗收方式：部署更新後查詢實際呼叫紀錄，便能把「版本符合條件」推進到「這筆連線確實使用了混合式金鑰交換」，也方便日後持續檢查。

通鑑怎麼看

通鑑認為，這次更新的價值在於把後量子保護接進既有的機密資料擷取流程，並提供可從呼叫紀錄確認的驗收方法。企業採用時，應從使用中的用戶端與版本盤點起，最後以實際連線紀錄確認結果。
