用 AI 寫軟體自學地圖

不用先當工程師。先學會三件事：把要做的東西講清楚、讓 AI 動手、自己驗收。程式底子只補剛好夠用的那一塊——夠你看得懂它改了什麼、改壞了退得回去、上線前知道要檢查什麼。後面附完整目錄，要找更多時再往下翻。

明天就能開始的三門

  1. 01
    Anthropic — Claude Code 101
    全免費、12 堂、官方標 1.5 小時，完成有徽章。從「寫程式的 AI 代理跟聊天機器人差在哪」講起，核心是一套每次都能照走的節奏：先讓它讀、再讓它提計畫、你看過才動手、做完存一個版本。要實際操作需要 Claude 的付費方案（Pro 以上）或 API 帳號。
  2. 02
    Harper Reed — My LLM codegen workflow atm
    一篇文章，約 15 分鐘讀完。三步：先跟 AI 一問一答把想法磨成規格，再把規格拆成一步一步的計畫，最後照計畫一次做一步。這張地圖所有路線都建立在這個順序上。範例用的工具名稱可以跳過，看流程就好。
  3. 03
    GitHub Skills — Introduction to GitHub
    不到 1 小時、免費、在瀏覽器裡就能做完。學的是「存版本」：AI 一次改幾十個檔案很正常，改壞的時候，有存版本的人按一下退回去，沒存的人只能重來。先學這個，再放手讓 AI 改。

怎麼走

先決定你要做的是哪一種。三條路線需要的底子不同，驗收方式也不同 —— 看完課不算學會，做得出下面那個「產出」才算。

三條路線

做給自己用的小工具不用會寫程式
  1. Claude 101 — 2.5 小時，先把 Claude 本身用熟：怎麼描述需求、專案、Artifacts（部分功能要付費方案才能實際操作）
  2. Claude Code 101 — 1.5 小時，換成會自己動手改檔案的版本
  3. Harper Reed 的三步流程 — 想法 → 規格 → 計畫 → 照做
  4. Introduction to GitHub — 1 小時，學會存版本
  5. GitHub Pages 快速入門 — 把做好的網頁放上網，免費

產出挑一件你每週都在做的重複工作，做成一個單檔網頁小工具，放上 GitHub Pages。給一個朋友用，把他卡住的地方記下來，改出第二版。

做給別人用的產品願意學一點程式
  1. MIT The Missing Semester 2026 — 挑四講：命令列環境、版本控制與 Git、打包與出貨（Packaging and Shipping Code）、代理式寫程式（Agentic Coding）。2026 年這一版把「跟 AI 代理一起寫程式」正式排成一講，大學課裡很少見
  2. 台大 — 用 Python 做商管程式設計（孔令傑）前幾講 — 中文、從零開始，目的不是自己寫，是看得懂 AI 寫的東西
  3. Claude Code in Action — 1 小時，讓它長時間自己做、你事後驗收的方法（先修：會用 Git 和命令列）
  4. GitHub 的推送防護（push protection）與從儲存庫移除敏感資料兩篇官方文件 — 金鑰不小心推上去時怎麼辦：先換掉金鑰，再清歷史
  5. OWASP Top 10 for LLM Applications 2025 — 你的產品如果也接了 AI，看第 1 名（提示注入）和第 2 名（敏感資訊外洩）就好

產出做一個別人下載或打開就能用的小產品，附安裝說明。推上 GitHub 前開啟推送防護，並寫一份自己的「出貨前檢查清單」，至少包含四項：有沒有夾帶金鑰或個資、測試是否全過、檢查腳本本身有沒有在說謊、線上是不是真的更新了。每次出貨照著勾一遍。

已經是工程師，改成跟 AI 代理一起工作會寫程式
  1. Claude Code 官方最佳實踐 — 官方持續改寫的版本，驗證、計畫模式、CLAUDE.md、平行工作都在這
  2. Simon Willison — Here's how I use LLMs to help me write code — 長文，核心一句：規格越清楚越快，測試永遠不能省
  3. Kent Beck — Augmented Coding: Beyond the Vibes — TDD 的提出者區分「只看結果的 vibe coding」與「在意程式碼品質的 augmented coding」（部分內容要付費訂閱）
  4. Birgitta Böckeler — Exploring Generative AI 系列 — martinfowler.com 上，Thoughtworks 團隊從 2023 年寫到現在的第一手實驗紀錄，挑標題看
  5. Missing Semester 2026 — Code Quality 一講

產出挑一個真實的小功能，先寫規格和測試，再交給代理做。記錄三個數字：你中途介入了幾次、測試抓到幾個它自己沒發現的錯、跟你自己寫比多花或省了多少時間。

為什麼要花時間在「驗收」和「安全」

AI 寫得快，漏得也快。資安公司 GitGuardian 的《State of Secrets Sprawl 2026》報告：2025 年公開 GitHub 上新增 2,865 萬筆寫死在程式裡的金鑰，一年增加 34%，是他們紀錄以來最大的單年增幅；其中由 Claude Code 協助的存版本，金鑰外洩率 3.2%，全體平均是 1.5%。

工具本身不是問題，問題是做得太快、沒有人檢查。路線二的那份出貨前檢查清單就是為了這件事。

本站自己踩過的四個坑

Fervela 的軟體都是這樣跟 AI 一起做出來的。下面四件事都真的發生過，共通點是：它們看起來都像成功——指令跑完、沒有紅字，問題要到別人手上才會出現。

1　發佈的檔案夾帶了不該有的東西

打包時順手把設定檔、本機路徑、私人信箱一起包了進去。教訓：發佈前用工具掃一遍成品，不是掃原始碼。

2　檢查腳本說「全部通過」，其實根本沒跑

一個指令寫法錯了，掃描沒有執行，結果是空的，於是印出「乾淨」。教訓：「工具沒跑起來」和「檢查通過」必須是兩種不同的結果；一個永遠不會失敗的檢查，比沒有檢查更危險。

3　覆蓋舊的下載檔，下載次數歸零

為了省一個版號，把新檔案蓋在已發佈的版本上，累積的下載數字一起消失，救不回來。教訓：已經發出去的東西不要覆蓋，有問題就發新版。

4　推上去成功了，網站卻還是舊的

推送指令回報成功，但網站的建置在後面失敗，沒有人發現。教訓：上線後打開真正的網址，確認看到的是新內容，才算上線。

路線二那份出貨前檢查清單的四項，就是從這四個坑來的。
