什麼是「迴圈工程」？

一句話重點

「迴圈工程」（loop engineering）是把開發者的角色從「親自對 AI 下提示」轉成「設計會自動反覆提示 AI 的迴圈」；公開部分談定義、來源、現成指令與實際用法。

這篇在講什麼

作者觀察到，幾位知名開發者開始說自己不再直接對程式代理人（coding agent）下指令，而是寫一個迴圈，讓程式去反覆驅動代理人。文章先交代這個說法的起點與演變，再整理各個工具內建的迴圈功能，最後根據作者蒐集的大量網友回覆，歸納大家實際拿迴圈做什麼。後半談失望與成本等議題，屬付費內容。

重點整理

定義：把「下提示的人」換掉

  • 有人把迴圈工程形容為取代自己「負責對代理人下提示的那個人」。
  • Claude Code 的創作者曾公開表示，他不再直接提示模型，而是跑迴圈去提示它，自稱工作就是寫迴圈。
  • 另一位代理人工具創作者也在推廣設計迴圈的做法。

源頭：Ralph 迴圈

  • 起點是 Geoffrey Huntley 提出的做法，最簡單的形式就是用 Bash 腳本反覆把同一份提示檔餵給代理人。
  • 流程是先寫好含成功條件的計畫，每圈只處理一項，檢查目標是否達成，沒達成就用乾淨的上下文（context）重新啟動代理人。
  • 2025 年底因 Matt Pocock 的教學而流行：維護一份持續更新的產品需求文件（PRD）與進度紀錄，測試通過才提交一項功能，作者形容像動態看板。
  • 主要動機是繞開上下文視窗的限制：把進度存在檔案系統、讓代理人每次從乾淨狀態開始，可減輕「上下文腐化」（context rot，內容塞滿後表現變差）。

工具內建的迴圈指令

  • Claude Code 在 3 月加入 /loop，可依間隔重複執行任務直到完成。
  • Codex 在 4 月推出 Goals，讓同一串對話朝既定目標跨回合持續工作。
  • Hermes agent 在 5 月 2 日推出 /goal，據稱受 Codex 啟發；Claude Code 5 月 12 日也推出 /goal，每回合後由一個小而快的模型判斷完成條件是否成立。
  • 也出現了開源的對應外掛與套件。

實際用途：觸發與排程

  • 作者蒐集約 210 則回覆（多來自 X 與 LinkedIn），歸納出兩大類。
  • 觸發型（trigger）：事件發生時啟動代理人，例如出現錯誤紀錄、新工單、客戶回饋；過去多靠 webhook、Slack 機器人、Zapier、n8n 完成。
  • 排程型（cron job）：定時執行代理人。有主管質疑這並不新，因為重複性工作在大型語言模型出現前就能自動化。

開發者分享的例子

  • 定時檢查錯誤監控、為新問題開 PR（拉取請求），並提醒未審的 PR。
  • 用 /loop 反覆修不穩定的測試，累計開出 13 個 PR。
  • 分析警報、實作修正、開 PR，再請人類審查。
  • 讓代理人反覆審設計文件，直到找不到新的重大問題。
  • 讀取 24 小時的日誌與使用者回饋，草擬修正，仍由人審。
  • 調查夜間端對端測試失敗，嘗試修復，超過重試上限就上報。
  • 另有人用每 30 分鐘的排程，把 React 應用逐步轉成 React Native。

公開部分的預告：失望與成本

  • 文章開頭提到，有些開發者試過後放棄，原因包括代理人會偏離方向，以及有人參與的流程成果更好。
  • 在按 API 計價的公司，迴圈的成本也會快速上升。
  • 這部分的詳細論述在付費區，本整理不展開。

對學習者的意思

  • 先弄懂單次提示與上下文管理，再談迴圈；迴圈的許多設計就是為了繞開上下文限制。
  • 迴圈的核心是「明確的完成條件」加「每圈可檢查的小步驟」，沒有這兩樣就容易空轉。
  • 現有的事件觸發與排程自動化觀念，可直接搬來理解代理人迴圈，不必當成全新領域。
  • 別人的例子多半仍保留人工審查（PR 由人看），初學時照這個節奏較穩。

要小心的地方
