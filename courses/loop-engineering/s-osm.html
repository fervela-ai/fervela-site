一句話重點

迴圈工程（loop engineering）就是不再一輪一輪親自對程式代理人（coding agent）下指令，而是設計一套會自己找事、派工、檢查、記錄、決定下一步的系統；但最後該負責把關的人，仍然是你。

這篇在講什麼

作者觀察到，過去兩年大家用 AI 寫程式的方式，多半是寫提示、看結果、再打下一句。現在相關工具把排程、平行工作區、專案知識、外部連接和分工檢查都內建了，讓人可以把整個流程設計一次，之後由系統自己轉。作者認為這可能是代理人工作的未來走向，但同時強調目前還很早期，他自己也抱持懷疑，並提醒成本與驗證責任。

重點整理

什麼是迴圈

  • 迴圈是一種「遞迴式的目標」：你先定好目的，AI 反覆做到完成為止。
  • 文中引用業界人士的說法：工程師應該設計能去驅動代理人的迴圈，而不是直接對代理人下提示。
  • 一個完整的迴圈要能找出工作、交給誰做、檢查結果、記下進度、判斷下一步。

在整體架構中的位置

  • 最底下是「代理人外殼工程」（agent harness engineering），指單一代理人跑在什麼環境裡。
  • 作者先前還談過「工廠模式」（factory model），指整套產出軟體的系統，和代理人外殼工程是相關的概念。
  • 迴圈工程則是在它們之上：依時間觸發、自己叫出幫手、把自己的產出再拿回來當輸入。
  • 因為這些零件已經內建在各家產品裡，設計本身不綁定特定工具。

五個要素

  • 自動化排程（automations）：定時執行，負責發現問題與初步分類。
  • 工作樹（worktrees）：每個代理人有自己的工作目錄與分支，平行作業時不互相踩到。
  • 技能（skills）：把專案知識寫成文件，代理人就不必每次靠猜；它是一個資料夾，內有 SKILL.md 說明檔。
  • 外掛與連接器（plugins and connectors）：讓代理人接上議題追蹤、資料庫、測試環境和通訊工具，常透過 MCP；外掛則把這些打包方便分享。
  • 子代理人（sub-agents）：一個負責做，另一個負責驗，作者稱這是最有用的結構設計。

第六個零件：記憶與狀態

  • 需要一份放在對話之外的狀態檔或看板（例如 Markdown 檔或專案管理工具），記錄做完了什麼、下一步是什麼。
  • 這樣每次執行之間，進度才不會斷掉。

幾個細節

  • 作者列了對照表，說明 Codex 與 Claude Code 各自對應的功能，結論是兩邊能力大致相同。
  • 對話中的 /loop 指令會按固定節奏重複執行；/goal 則持續跑到達成條件為止，每輪由另一個小模型判斷是否達標，所以寫程式的那個代理人不會自己給自己打分數。
  • 平行跑多少代理人，真正的上限是人類能審查多少，而不是工具。
  • 子代理人會多耗詞元（token），應該用在值得有第二意見的地方。

範例流程

  • 早上由排程讀取 CI 失敗紀錄、未結議題和近期提交，把發現寫進狀態檔。
  • 值得處理的項目，開獨立工作樹，由一個子代理人草擬修改，另一個審查。
  • 再透過連接器開 PR、更新工單、通知團隊；解決不了的丟進人工待處理匣。
  • 重點是流程只設計一次，不是每一步都親自下提示。

對學習者的意思

  • 學寫迴圈，先想清楚五個要素加狀態檔各自負責什麼，再動手。
  • 可以從小處練習：一個定時任務、一份狀態檔、一個做事的角色加一個驗收的角色，就是最小的迴圈。
  • 「做的人」和「驗的人」要分開，別讓同一個代理人批改自己的作業。
  • 把反覆要講的專案規則寫成技能文件，是投資報酬率很高的第一步。
  • 迴圈該用來加速你已經看得懂的工作，而不是用來逃避理解。

要小心的地方

  • 驗證仍是人的責任：無人看管的迴圈也會無人看管地出錯，「完成」只是一種宣稱，不是證明。
  • 你沒親手寫的程式越多，你理解的內容與實際存在的內容差距越大（作者稱為理解債，comprehension debt），還可能不自覺放棄判斷（cognitive surrender）。
  • 成本變動大，子代理人會成倍增加詞元用量，需要持續盯著花費；作者也明說這個做法還在早期。
