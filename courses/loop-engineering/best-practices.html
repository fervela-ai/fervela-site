一句話總結

Claude 做完會自己停，但它只知道「看起來做完了」。你不給它一個能自己跑的檢查，你就變成那個檢查。 整份文件 90% 都在講這件事的各種做法。

0. 最重要的限制：對話視窗會滿，滿了就變笨

  • Claude 的「記憶」就是這個對話視窗。每句話、每個讀過的檔、每個指令輸出都佔位子。
  • 視窗越滿，表現越差：會忘記前面的規矩、開始犯錯。
  • 所以大部分做法都是為了「別讓視窗塞滿」。

1. 給 Claude 一個它自己能跑的檢查（全文最核心）

  • 沒有檢查，「看起來做完」是它唯一的訊號，每個錯都要等你發現。
  • 有檢查（會回「過／不過」的東西），迴圈自己閉合：它做→跑檢查→看結果→改→再跑，直到過。
  • 檢查可以是：測試、建置成功與否、程式碼檢查器、比對輸出的腳本、截圖跟設計稿比。
  • 檢查要多硬，四個等級由鬆到緊：
    1. 寫在同一句指令裡：「做完跑測試，不過就改」。
    2. 整個對話都守著：設一個「目標」（/goal），每一回合有另一個評分者重查，沒達標就不准停。
    3. 確定性的門：「停止 hook」（Stop hook，對話要結束前自動跑你的腳本，不過就不讓它停）。
    4. 第二意見：另開一個乾淨的子代理（subagent，沒看過過程的另一個 Claude）來推翻它的結果，做的人不能當評分的人。
  • 要它拿證據，不是宣稱做完：測試輸出、跑了什麼指令回了什麼、截圖。看證據比你自己重跑快，而且你不在場的工作也能這樣驗。
  • 三個改寫例子：「寫一個驗證信箱的函式」→「寫函式，測試案例：a@b.com 要過、invalid 不過；寫完跑測試」。「把儀表板弄好看」→「照這張截圖做，做完截圖跟原圖比，列差異修掉」。「建置壞了」→「錯誤訊息如下，修好並確認建置成功，要修根因不是把錯誤壓掉」。

2. 先探索、再計畫、再動手

  • 直接動手常常解錯問題。用「計畫模式」（plan mode，只讀不改）先讓它讀程式、回答問題，再要它列計畫，你看過才放手做，最後存版本。
  • 但小事不用：改錯字、加一行紀錄、改名，直接做。「一句話講得完的改動，跳過計畫」。

3. 指令要具體

  • 它能猜你的意思，但猜不到你腦子裡的。指名檔案、講限制、指向可以照抄的範例。
  • 例：「幫 foo.py 加測試」→「加一個測試，涵蓋使用者已登出的情況，不要用假物件」。「修登入的 bug」→「使用者回報逾時後登入失敗，看 src/auth 的權杖更新，先寫一個會失敗的測試重現它，再修」。
  • 可以直接貼檔案（@）、貼截圖、給網址、把資料灌進去。
  • 模糊指令在探索時有用：「這個檔你會改什麼？」能挖到你沒想到的。

4. 環境怎麼設

CLAUDE.md（每次開對話都會讀的規矩檔）

  • 放：它猜不到的指令、跟預設不同的風格、測試怎麼跑、分支命名、專案特有的架構決定、環境怪癖、不明顯的坑。
  • 不放：讀程式就知道的、標準慣例、詳細文件（給連結就好）、常變的資訊、長篇教學、「寫乾淨的程式」這種廢話。
  • 要短。每一行問自己：「拿掉這行它會犯錯嗎？」不會就刪。太長的 CLAUDE.md 會讓它忽略你真正重要的規矩。
  • 它一直做你不要的事、明明有規矩？多半是檔太長、那條被淹沒。它問你 CLAUDE.md 已經寫的問題？多半是那句寫得模糊。
  • 把 CLAUDE.md 當程式：出事就回頭看、定期修剪、改了要觀察行為有沒有真的變。
  • 只對一條加「IMPORTANT」有用；每條都加就沒有一條突出。
  • 偶爾才用的知識不放 CLAUDE.md，放 skill（技能檔，用到才載入）。

權限

  • 每個動作都問你很安全但很煩，問到第十次你就只是按過去。兩個解法：允許清單（你信任的指令預先放行）、沙箱（作業系統層級限制它能碰哪些檔案和網路，在框框裡隨便跑）。

用指令列工具、接 MCP

  • 跟外部服務互動，用指令列工具（例：gh）最省視窗；它不會的工具叫它先看 --help 自己學。
  • MCP 伺服器可以接工單系統、資料庫、設計稿。

hook（固定會跑的腳本）

  • 「必須每次都發生、零例外的事，用 hook。」 CLAUDE.md 是勸告，hook 是確定的。
  • 可以叫 Claude 幫你寫 hook：「寫一個 hook，每次改檔後跑檢查」「寫一個 hook，擋住對 migrations 資料夾的寫入」。

skill（技能檔）與子代理

  • skill：專案或領域知識、可重複的流程，放一個資料夾，它需要時自動用，或你打 /名稱 叫它。有副作用的流程設成只能手動叫。
  • 子代理：有自己獨立視窗、自己的工具權限，適合「要讀很多檔」或「要專注一件事」而不想弄髒主視窗。

5. 溝通

  • 問它你會問資深工程師的問題：「紀錄怎麼運作？」「為什麼這裡呼叫 foo 不是 bar？」不用特別的提示法。
  • 大功能先讓它訪談你：「我要做〇〇，用提問工具詳細訪談我：技術、介面、邊界情況、取捨，別問顯而易見的，挖我沒想到的，問完寫成規格檔。」然後開新視窗照規格做，乾淨的視窗只裝實作。
  • 好規格的樣子：寫明檔案與介面、寫明不做什麼、最後一步是「端到端驗證怎麼證明它能用」。花時間把規格寫準，比花時間盯著它做划算。

6. 管理對話

  • 早糾正、常糾正：發現歪了馬上按 Esc 停、Esc Esc 倒帶到之前的狀態、「撤銷」、/clear 清空換題。
  • 同一件事糾正超過兩次還錯：視窗已被失敗的嘗試污染，/clear 重來，用一句更好的第一句話把學到的寫進去。「乾淨視窗＋好的第一句，幾乎總是贏過長視窗＋一堆糾正。」
  • 不相關的任務之間 /clear；長對話會自動壓縮，可以在 CLAUDE.md 寫「壓縮時一定保留改過的檔案清單與測試指令」。
  • 研究用子代理，別讓讀檔佔主視窗。
  • 每次送出都是一個存檔點，可以倒帶對話或程式；大膽試，不行就倒帶。（倒帶只管 Claude 自己改的檔，不是 git。）
  • 對話可以命名、續接，像分支一樣每條工作線一個。

7. 自動化與放大

  • 非互動模式：claude -p "指令" 可以放進排程、腳本、CI，輸出可以是純文字或 JSON，接進資料管線。
  • 多視窗平行：各開一個工作複本（worktree）互不打架；視窗之間可以傳訊息；桌面版可視覺化管理；雲端版在 Anthropic 機器上跑。
  • 寫手／審查者分兩個視窗：A 寫，B 用乾淨視窗審「邊界情況、競爭條件、跟既有模式一不一致」，再把 B 的意見給 A 改。乾淨視窗審查更公正，因為它不偏袒自己剛寫的。也可以一個寫測試、另一個寫程式去過測試。
  • 大批量展開：2,000 個檔要搬，先列清單，寫一個迴圈對每個檔叫 claude -p，先試 2～3 個修好指令再全跑。
  • 自動模式：有一個分類模型在背後審每個指令，擋升權、不明基礎設施、被惡意內容驅動的動作，其餘不問直接跑。
  • 對抗式審查：當成「做完」之前，開一個乾淨子代理只看差異和你給的標準，報缺口；但要叫它「只報影響正確性或需求的，其他算選配」，否則它一定會找出東西來、你會過度工程。

8. 常見失敗（五種）

  1. 大雜燴視窗：一個題做到一半問別的又回來。→ 不相關就 /clear。
  2. 糾正不完：錯、糾正、還錯、再糾正。→ 兩次沒好就清空重來。
  3. CLAUDE.md 過長：重要規矩被淹沒。→ 狠心刪；它不用規矩也做對的，刪掉或改成 hook。
  4. 信了沒驗：看起來合理但邊界沒處理。→ 一定給驗證；「驗不了就不要出貨」。
  5. 無止境探索：「幫我研究一下」沒劃範圍，它讀幾百個檔把視窗塞滿。→ 劃小範圍或交子代理。

9. 培養直覺

這些不是鐵律。有時候該讓視窗累積（你在一個難題裡，歷史有價值）；有時候該跳過計畫（探索性的事）；有時候模糊指令正好（想看它怎麼理解）。它做得好時注意你做了什麼，做不好時問為什麼：視窗太吵？指令太糊？一次做太大？
