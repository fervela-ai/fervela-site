為 AI 代理做有效的脈絡工程

一句話重點

模型每一步能看到的內容（脈絡，context）是有限的注意力預算，好的代理要做的是只留下最有用的少量資訊，而不是一直往裡面塞。

這篇在講什麼

作者把「脈絡工程」（context engineering）定位成提示工程（prompt engineering）的延伸：提示工程在寫好指令，脈絡工程則要管理模型推論時看到的全部內容，包括系統提示、工具、外部資料與對話歷史。文章先解釋為什麼脈絡越長不一定越好，再說明怎麼設計脈絡、怎麼讓代理邊做邊找資料，最後介紹三種處理長時間任務的做法：壓縮、做筆記、拆給子代理。

重點整理

什麼是脈絡工程

  • 脈絡指的是模型取樣時所帶入的全部詞元（token）。
  • 核心問題是：什麼樣的脈絡配置，最可能讓模型做出想要的行為？

為什麼脈絡要節制

  • 詞元變多時，模型找回資訊的準確度會下降，作者稱為脈絡腐化（context rot）。
  • 退化是漸進的，不是突然懸崖，所以脈絡應視為邊際效益遞減的有限資源，也就是「注意力預算」（attention budget）。

好脈絡的組成

  • 總原則：找出最小的一組高訊號詞元，讓期望結果最可能出現。
  • 系統提示要抓對「高度」：不要寫成脆弱的 if-else 規則堆，也不要模糊到沒有具體訊號。可用 XML 標籤或 Markdown 標題分區。
  • 工具要自成一體、參數清楚、省詞元；工具集太肥、功能重疊是常見失敗，人類工程師分不清用哪個，代理也分不清。

執行時才取資料（just-in-time）

  • 原文把代理簡化定義為「在迴圈中自主使用工具的 LLM」。
  • 傳統做法是先用嵌入（embedding）檢索把資料預先塞進去；即時取用則是只帶檔案路徑、查詢、連結等輕量識別，需要時才用工具載入。
  • 代價：執行時探索比預先檢索慢，而且需要好的工具與引導，否則會在死路上浪費脈絡。
  • 折衷是混合式：一部分先載入求速度，其餘讓代理自行探索。原文舉的例子是先讀 CLAUDE.md，再用 glob、grep 即時查找。

長時間任務一：壓縮（compaction）

  • 做法是脈絡快滿時，請模型摘要，再用摘要開新視窗。
  • 摘要保留架構決策、未解錯誤、實作細節，丟掉重複的工具輸出。

長時間任務二：結構化筆記（agentic memory）

  • 代理把筆記寫到脈絡以外的地方（例如待辦清單、NOTES.md），之後再讀回來。

長時間任務三：子代理架構（sub-agent）

  • 主代理負責整體計畫，子代理在乾淨的視窗裡處理聚焦的任務。
  • 子代理內部可能用掉數萬詞元，但只回傳約 1,000 到 2,000 詞元的精簡摘要。

對學習者的意思

  • 寫代理迴圈時，每一輪都要問：下一步真正需要看到什麼？不要把所有歷史原封不動帶著跑。
  • 工具設計是脈絡設計的一部分：少而清楚、不重疊，輸出也要精簡。
  • 資料可先只存「指標」（路徑、查詢），迴圈裡再用工具取，這能讓脈絡保持乾淨。
  • 任務拉長時，三招可依情境選：對話來回多用壓縮，有里程碑用筆記，要平行研究用子代理。

要小心的地方

  • 原文沒有專門的限制章節，但自承即時探索較慢、需要好工具；壓縮過度會遺失日後有用的細節。
  • 三種長任務技術各有適用情境，沒有通用最佳解；Claude Code 與寶可夢的例子是說明用，不是對照實驗的結果。
  • 作者也說，隨著模型變強，提示格式等細節的重要性可能下降，所以文中某些具體建議未必長期適用。
